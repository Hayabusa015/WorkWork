| # | Operation | Status |

| 3 | upload `SHULL_CHEM_Slides_U01_S01.4.pptx` | **BLOCKED** |

`mcp__Google_Drive__create_file` accepts file content only **inline**, as `textContent` or
`base64Content`. There is no path-based upload. So a binary deliverable has to pass through the
agent's context as base64 to reach Drive.

Measured on this file:

| | |
|---|---|
| Deck as written by pptxgenjs | 591,361 bytes |
| Repacked with maximum deflate, diagram resampled to 1800px | **109,198 bytes** |
| As base64 | **145,600 characters** |
| Largest tool output that renders in full | **under ~35,000 characters** |

So the file cannot be read out in fewer than six pieces and then re-emitted as a single 145,600-character
parameter. Every character has to survive that round trip by hand.

**Stopped deliberately.** One wrong character produces a corrupt `.pptx` sitting in the folder
Matthew teaches out of, and a corrupt file that *looks* filed is worse than one that is plainly not
filed. The cost is real and the failure is silent.

The repack is worth keeping regardless: **591 KB → 109 KB, byte-identical rendering**, verified by
re-running the geometry audit, `pdffonts`, and a page-by-page text comparison against the original
render. pptxgenjs writes its zip almost uncompressed.

## What this means beyond this one file

**The Librarian cannot file the things the Designer builds.** Not this deck specifically — any
`.pptx`, any `.docx`, any PDF above roughly 25 KB. Folder creation, renaming, reparenting, metadata
and text files all work; binary deliverables do not.

`docs/SHULLOS_IMPLEMENTATION_PLAN.md` §8 says the human is the bridge for Project Knowledge and that
Drive is the shared read path both surfaces reach. **Drive is the shared read path. It is not a
write path for built binaries.** The human is the bridge there too.

Recorded in §21 Known Limitations and in `.claude/agents/librarian.md`, because an agent whose
stated authority exceeds what it can actually do will keep reporting success it did not achieve.
